# FD-26: разбор ошибок M2 (E7)

## Метод

- Модель: `microsoft/unixcoder-base @1024` (`config/train_best.yaml`),
  калиброванная `p_cal` (`reports/calibration.json`, T=2.3847),
  рабочий порог `tau=0.8742609896291749` (FD-25, precision>=0.80 на `val`).
- Ошибки: `(p_cal >= tau) != label_stale`, только `gold` + `test_real`.
  Полная перепись всех 210 ошибок (gold 62: FP 57 + FN 5; test_real 148:
  FP 44 + FN 104), а не подвыборка 50+50: при полноте (recall) M2 на `gold`
  90.9% (50/55) FN всего 5 — набрать 50 FN на `gold` физически невозможно;
  перепись генеральной совокупности исключает selection bias.
  Отбор детерминирован (`scripts/select_fd26_errors.py`, сортировка по `pair_id`,
  `err_id` e001…e210; усечение тем же `encode_pair`, что видел M2).
- Разметка: две независимые слепые R9-разметки всех 210 (батчи
  `reports/fd26_batches/` 6×35, задание `prompts/fd26_annotate.txt`;
  батчи не содержат split/source/меток — только diff+docstring).
  Сведение `scripts/combine_fd26.py`, 28 споров разрешены человеком
  (`reports/fd26_disputes_labeled.csv`; оценка человека объективна).
- Согласие прогонов: 182/210 (86.7%), каппа Коэна 0.674 (4-класс, явные labels)
  / 0.733 (бинарно A/B→1, C→0; D исключён) — выше планового бара workflow
  0.35–0.50; схема двойной слепой разметки с арбитражем воспроизводима.
  Человек сошёлся со Spark на 10/28 спорах, с Gemini на 17/28;
  в 1 споре (e017) выставил D, не совпавший ни с одним из прогонов (10+17+1=28).
- Итоговая метка: консенсус LLM, споры — вердикт человека:
  C156 / A33 / B20 / D1. Бинарно: stale=53, fresh=156, D=1.
- Причина каждой строки — колонка `cause` файла `reports/fd26_combined.csv`
  (эксклюзивные правила приоритета: D → шум метки → усечение → FN →
  сигнатурный FP → нейтральный FP; ручной override через колонку `cause`
  в human-файле — в т.ч. доступна категория `complex_docstring`,
  автоправилами не назначаемая).

## Причины ошибок по сплитам (доли от сплита, 95% бутстрэп-CI)

| Причина | gold (n=62) | test_real (n=148) |
|---|---|---|
| Шум метки (тройка за M2) | 5 (8.1% [1.6,16.1]) | 67 (45.3% [37.2,52.7]) |
| Особенность кода: сигнатурный дифф без покрытия в доке (FP) | 32 (51.6% [38.7,64.5]) | 0 (0.0%) — в `test_real` отрицательные пары по построению без смены сигнатуры |
| Особенность кода: нейтральный рефакторинг тела (FP) | 18 (29.0% [17.7,40.4]) | 38 (25.7% [18.9,33.1]) |
| Особенность кода: пропуск изменения логики/возврата без смены параметров (FN) | 4 (6.5% [0.0,12.9]) | 41 (27.7% [20.9,34.5]), из них 35 без смены сигнатуры + 6 с изменением возврата |
| Усечение входа | 2 (3.2% [0.0,8.1]): e110, e113 | 2 (1.4% [0.0,3.4]): e146, e160 |
| Другое: нужен внешний контекст (D) | 1 (e017) | 0 |

Проверка: 5+32+18+4+2+1 = 62; 67+0+38+41+2+0 = 148. Истинных ошибок M2 —
137 (gold 56 + test_real 81); FP среди них — 32+18+38+4 = 92/137 (67.2%).
Категория «сложный docstring» автоправилами не назначена ни разу:
длинные доки (>1000 символов) — всего 8 строк, все FP с очевидным
перетриггером; тонкие доки сконцентрированы в шуме меток (61/72), а не в
ошибках модели (тонкий = длина <80 символов или <3 переводов строки;
пограничные e130, e139 — 4-строчные доки ≥80 символов). Ветка
`complex_docstring` оставлена в коде для ручной классификации такого случая.

Флаги усечения встретились у 5 строк; e106 (`InstaPy/follow_user`, test_real FN,
p=0.624) консенсусом C отнесена к шуму метки (модель права, метка датасета
ошибочна) — в категорию усечения входят оставшиеся 4 строки, являющиеся
истинными FP-ошибками модели. Флаги фиксируют возможный вклад, не доказанную
причинность (вердикты C вынесены и по полному доку); e113 — единственный спор
с флагом (spark C vs gemini B, human C).

## Примеры для записки

1. **e196, gold FP, p=0.984** — `InstaPy/verify_liking`: переименование
   max/min→maximum/minimum; в docstring это обычные слова, имён параметров нет.
   Тройка: C. Учебный случай переоценки сигнатурного диффа.
2. **e033, gold FN, p=0.405** — `AzurLane/EventStory.get_event_story_state`:
   новое возвращаемое `'story_alchemist'` вне перечня Returns.
   Тройка: A (спор, разрешён человеком). Пропуск без смены сигнатуры.
3. **e044, test_real FP, p=0.969** — `manim/Line3D.perpendicular_to`:
   расширение типа point и замена array на asarray; описанное поведение
   не изменилось. Тройка: C. Нейтральный рефакторинг с высокой уверенностью.
4. **e205, test_real FN, p=0.410** — `pandas/extract_pandas_array`:
   классы переименованы в NumpyExtensionArray/NumpyEADtype, названия
   в доке устарели. Тройка: A (спор, разрешён человеком). Пропуск,
   где stale виден только по именам в доке.

## Выводы для записки

- Главный режим отказа M2 — переоценка изменения кода: 92/137 истинных ошибок
  (67.2%) — FP, где модель стреляет по форме диффа, не проверяя docstring;
  на `gold` 52/57 FP подтверждены тройкой (уверенность до 0.987 при консенсусе C).
- На `gold` доминируют FP (52/56 истинных, 92.9%), из них `sig_overtrigger`
  32/56 (57.1%); FN — всего 4/56 (7.1%). На `test_real` картина иная:
  FN 41/81 истинных (50.6%), а `sig_overtrigger` равен 0/81 — в `test_real`
  отрицательные пары по построению без смены сигнатуры, поэтому объединять
  сплиты в один пул нельзя: природа ошибок разная.
- Разрыв `test_real`/`gold` частично объясняется шумом слабых меток
  (63/104 `test_real` FN — шум), поэтому честная оценка — только `gold`.
- Усечение входа (2.9% истинных: 4/137; по сплитам gold 3.2%, test_real 1.4%)
  и внешний контекст (1 строка) на качество практически не влияют;
  резерв — признаки покрытия doc↔sig и расширение P1.

  `scripts/fd26_cause_ci.py`
